# The document set

*A portable reference, extracted from a long engagement on a metadata-driven
app platform and kept here because it applies to every project, not that one.*

Most projects do not suffer from too few documents. They suffer from documents
that were true once. A design note describing a module three refactors ago, a
coverage matrix last regenerated by hand in March, a README whose setup steps
fail on a fresh checkout — each of these is worse than nothing, because a
reader cannot tell which parts still hold and so stops trusting all of them.

The way out is not more discipline. It is arranging documents so that staying
true is structural.

## The design rule

> Judgment lives in the spec, mechanics live in one living doc, history lives
> in append-only logs, and every relationship between documents is checked by
> CI rather than maintained by discipline. Everything that stays true is either
> executable or sits next to the thing it describes; everything that drifts is
> a document about another artifact at a distance.

Read the second sentence as a test you can apply to any file in the repo. Is
this thing executable — a test, a check, a script? Then it cannot quietly rot;
the build says when it stops being true. Does it sit next to what it describes
— a comment above the function, a rule ID in the test name? Then a change that
invalidates it is in the same diff as the change itself, in front of the same
reviewer.

Otherwise it is a *document about another artifact at a distance*: a file that
claims something about code it does not live in and cannot check. That is the
anti-pattern, and every drifting artifact you have ever met is an instance of
it.

## The minimal set, by the question each answers

> The minimal document set: a constitution file (CLAUDE.md — "what must never
> happen, and where is everything?"); one spec per capability with rule IDs,
> example tables as acceptance criteria, and a verdict line per rule ("what
> should this do, how do we know, how proven is it?"); tests carrying spec IDs
> in their names as the executable evidence, with a CI check enforcing the
> spec↔test linkage; one living how-to doc (TESTING.md — "how do I write and
> run a test here, where does it go?"); an append-only journal (PROGRESS.md —
> "what happened, what bit us, what's next?"); append-only decision records
> (ADRs — "why is it this way?"). Hand-maintained cross-reference matrices are
> retired in favor of generated reports + CI checks.

Six kinds of file. Each earns its place by answering a question no other file
answers.

### A constitution file — `CLAUDE.md`
**"what must never happen, and where is everything?"**

The invariants, the hard rules, and the map to everything else. Short enough
to be read in full at the start of every session, and stable enough that
re-reading it rarely surprises. It is not documentation of the system; it is
the standing protocol for working on it.

### One spec per capability
**"what should this do, how do we know, how proven is it?"**

Rule IDs, example tables as acceptance criteria, and a verdict line per rule.
The example table *is* the acceptance criteria — not an illustration of them —
so there is no second place where the expected behaviour lives and no chance
for the two to disagree. The verdict line carries the third question: is this
rule specified only, covered by a test, or proven end-to-end? Judgment lives
here, and nowhere else: what the system should do is a decision, and decisions
belong in a document a human ratifies.

### Tests carrying spec IDs in their names
**The executable evidence.**

The test name contains the rule ID it discharges, and a CI check enforces the
spec↔test linkage in both directions: a rule with no test is visible, a test
naming a rule that no longer exists fails. This is what replaces the
traceability matrix — the linkage is derived from the artifacts themselves,
every run, rather than transcribed by someone who remembered to.

### One living how-to doc — `TESTING.md`
**"how do I write and run a test here, where does it go?"**

Exactly one. Mechanics — the commands, the fixtures, the conventions, the
layout — in a single file that is edited in place rather than appended to.
When there are two such documents, both are wrong within a month, because
nobody knows which one to update.

### An append-only journal — `PROGRESS.md`
**"what happened, what bit us, what's next?"**

Dated entries, never edited after the fact. Because it is append-only it
cannot drift: an entry from March is a true record of March, not a stale claim
about today. It is where the gotcha that cost three hours gets written down,
and where the next session picks up.

### Append-only decision records — ADRs
**"why is it this way?"**

One file per decision: the context, the choice, the consequences. Superseded
by writing a new one, never by editing the old one — the record of a decision
you later reversed is exactly the thing that stops you reversing it back next
year.

## What this retires

Hand-maintained cross-reference matrices. The coverage spreadsheet, the
requirements-to-test grid, the "which spec covers which module" table. They
are documents about artifacts at a distance, in the purest form — a
transcription of relationships that already exist in the code and the specs,
kept in sync by someone's memory.

Replace each one with a **generated report plus a CI check**. The report is
derived from the artifacts on every run, so it is never stale. The check fails
the build when the relationship it asserts stops holding, so the linkage is
enforced rather than described.

## How this library makes conventions structural

Two of the pieces in this package exist to move a convention out of a style
guide and into a mechanism:

- **`session.until(description, fn)`** gives "don't sleep in tests" an honest
  alternative. A rule with no alternative is a rule people break under
  deadline; a rule with a first-class verb behind it is just how you write the
  test. The mandatory description means the failure names the awaited
  condition — `[FAILED] until: the export job finishes` — so the trace teaches
  the reader what the test was waiting for.
- **The [ESLint plugin](../README.md#lint-plugin)** turns the review comments
  a suite audit produced into checks: no sleeps, no conditional skips, no weak
  assertions, no swallowed cleanup errors, serial mode annotated. Each message
  names the preferred alternative, so the error itself does the teaching —
  which is what "executable, not documented at a distance" means in practice
  for a convention.

The same test applies to your own conventions. If it is written in a document
about the code, it will drift. If it is a lint rule, a verb, a CI check, or a
comment on the line it constrains, it will not.
